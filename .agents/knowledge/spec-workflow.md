# Specification Workflow Contract

Read before starting a change that alters what the plugin or its tooling does, before creating an issue from a
specification, and before editing any file under `openspec/`.

Specification level: spec-anchored. Selected because the plugin's components are a contract other people install and the
template's generation rules are a contract adopters build on; both outlive any one change. Obligation: every merged
change to plugin behavior leaves `openspec/specs/<capability>/spec.md` describing the behavior as merged. Approach:
OpenSpec (schema `spec-driven`), layout and commands verified from `openspec --help` with OpenSpec 1.15.0 on 2026-10-26.
Re-verify a command with `openspec <command> --help` before running or documenting it. OpenSpec's generated skills
(`.agents/skills/openspec-*`, linked from `.claude/skills/`) are the command surface; the checks below are this
project's own.

## Artifact operations

Creating a change, validating, syncing, and archiving run through OpenSpec's commands or its generated skills; never
create `openspec/` directories or change metadata by hand. Hand edits stop at the text of proposal, design, tasks, and
delta specs. Validation: `just spec-check` runs OpenSpec's validator in strict mode over all specs and changes, checks
that every rule in `openspec/config.yaml` reaches OpenSpec (quote a rule containing a colon followed by a space), and
checks that the generated skills equal what `openspec init --tools agents` produces. Run it after every artifact edit,
before publishing the draft PR, before marking the PR ready, and after archiving.

## Artifact map

| Path                                                            | Holds                                                                                                                               | Edited by                                                        |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `openspec/config.yaml`                                          | Project context and per-artifact rules OpenSpec injects into its instructions; points to the knowledge base instead of restating it | Maintainer; agents propose edits in a PR                         |
| `openspec/specs/<capability>/spec.md`                           | Current behavior of one capability (Capabilities)                                                                                   | The archive step only                                            |
| `openspec/changes/<change-name>/`                               | One change: `proposal.md`, `design.md` when warranted, `tasks.md`, `specs/<capability>/spec.md` deltas, `.openspec.yaml`            | The change's author                                              |
| `openspec/changes/archive/<date>-<change-name>/`                | Archived changes, frozen                                                                                                            | The archive step only                                            |
| `.agents/skills/openspec-*/`, `.agents/skills/.openspec-target` | OpenSpec's generated skills                                                                                                         | Regenerated by `openspec init --tools agents`; never hand-edited |

Regenerate with `openspec init --tools agents`, never `openspec update`: the generic `agents` tool writes one skill set
under `.agents/skills/`, which Codex, Antigravity, Pi, and OpenCode read directly and Claude Code reads through the
symbolic links in `.claude/skills/`. `just spec-check` fails when the committed skills drift from `init`'s output
(`scripts/validate/check_openspec.ts`).

## Capabilities

One spec per capability, named for what it delivers, not for a file: `plugin-manifest`, `todo-scan`, `todo-triage`,
`todo-triager-agent`, `todo-mcp-server`, `platform-hooks`, `pi-package`, `generation`. A new component type gets a new
capability in the change that adds it; a framework integration that changes how an existing capability is delivered
edits that capability. The capability list is whatever `openspec/specs/` holds; this paragraph only says how to name
one.

## Artifact roles

| Artifact    | Owns                                                                                                                                                                                   | Never holds                                    |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| proposal    | The end state: why, the goal, what changes, the capabilities whose contracts change, and `## Acceptance`                                                                               | The contract itself, the approach, steps       |
| delta specs | The executable contract: requirements and scenarios of plugin behavior as a framework observes it                                                                                      | Implementation choices                         |
| design      | How the end state is reached: approaches discussed, decisions with rejected alternatives, constraints and invariants with how each is checked, information needed only for this change | The goal or acceptance, steps                  |
| tasks       | Implementation steps, each with its own verification; written only after the package gate closes                                                                                       | Acceptance; anything the package gate must see |

- `## Acceptance` has two lists of checkable items: **Becomes true** and **Stays true**. For plugin behavior it points
  to the delta specs' scenarios instead of restating them.
- A scenario describes what a framework or a user observes (a file generated, a tool answering, a hook message), never
  the diff that produces it.

## Source of truth

| Fact                                                | Rules                                                                  | Points to it                                     |
| --------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| What the template is for                            | `README.md`                                                            | `AGENTS.md`                                      |
| Component sources, discovery rules, conversion rule | `.agents/knowledge/architecture.md`                                    | `openspec/config.yaml`, specs never restate them |
| Framework facts and verification items              | `.agents/knowledge/frameworks.md`                                      | designs cite them                                |
| Behavior of a capability                            | `openspec/specs/<capability>/spec.md`                                  | issues, PRs, docs                                |
| Acceptance of a change                              | the proposal's `## Acceptance`, pointing to the delta specs' scenarios | PRs, issues                                      |
| The support matrix                                  | `docs/reference/support-matrix.md`                                     | specs and README link it                         |

A file under "Points to it" may summarize in one line and must link; it never restates the fact.

## Lifecycle

1. **Proposed**: the change is created with OpenSpec's propose flow, which stops before `tasks.md` (`rules.tasks`; a
   `tasks.md` a flow wrote anyway is deleted before the commit) and committed on the issue's branch; the draft PR opens
   with the complete approval package (proposal, delta specs, design when warranted) and the agent stops.
2. **Approved**: a maintainer adds `spec:approved` to the draft PR, or tells the agent to, and the PR labels workflow
   records the commit it approves (Approval gates).
3. **Implemented**: the agent writes `tasks.md` from the approved package (`openspec instructions tasks`), every task is
   done and every Acceptance item verified in the PR's Validation section; the PR is marked ready for the second
   deliberation.
4. **Archived**: only after a maintainer commands it in the conversation: the implementer runs OpenSpec's archive skill
   on the branch, which merges the deltas into `openspec/specs/` and moves the change to the archive. That commit is the
   freeze the final approval names.

## Approval gates

Both gates are owned by the maintainer (the repository owner, or a collaborator with write access); the package gate
closes on the pull request, the freeze gate in the conversation. An agent never passes a gate on a change it wrote. The
authority level is in `agent-authority.md`; these gates are where they attach.

The **package gate** releases the task list and the implementation. It is exercised on the proposal, the delta specs,
and `design.md` when warranted: always for a new component type or a new framework integration, and otherwise when more
than one reasonable approach exists or the change touches the generator's conversion rules, a manifest format,
dependencies, or files outside the change; a wording change inside one requirement needs none. The review covers goals
and scope, each scenario's observability from the framework's side, the support matrix rows the change moves, and the
design's bounds. A design lists no steps.

Mode of the package gate: the label `spec:approved` on the pull request. The maintainer adds it to the draft PR, or
tells the agent to in the current conversation, naming the pull request; the PR labels workflow
(`.github/workflows/pr-labels.yml`, `scripts/sync_pr_labels.ts`) records in one comment the commit it approves, the
account, and the label event, and keeps the label only while the approval package at the head (every file of each
unarchived change but its `tasks.md`, with the main spec of each capability the change has a delta for) equals the
package at that commit. A change to the package, a person removing the label or adding `spec:pending`, and a run the
workflow cannot stand behind each put `spec:pending` back. Read the gate by recomputing it, never from the bare label:
`just pr-labels <n>` prints the state the rules give the pull request now. A statement in the conversation does not
close this gate.

The **freeze gate** releases the archive, and the maintainer's final approval applies to the archived version. Mode:
conversational. It closes only on an explicit command to archive from the maintainer in the current conversation; a
command given in another session does not carry over. The PR is marked ready before the archive, so the `spec-archived`
check is withheld for the whole second deliberation (`github/checks.md`, Waiting for the archive): its absence is the
merge block, not a defect. Never archive to make it report. A commit after the archive commit means the approved version
no longer exists: say so and ask again.

Before acting on either closing, read the PR's comments and review threads with their resolution state, list every
unresolved thread, every requested adjustment the change does not carry yet, and every pair of contradicting
conclusions, confirm them with the maintainer, and proceed only when nothing is open or the open items are confirmed.

## PR shape

Combined. Selected because the plugin is installed from this repository by Git and version tag, so a specification on
`main` without its implementation reaches no one and needs no separate request.

One PR carries the whole lifecycle: it opens as a draft once the approval package is committed, with the package as its
only content; the package gate is exercised on that draft; tasks and implementation follow the approval and the
reconciliation; marking it ready requests implementation review; the archive follows the maintainer's command; the merge
closes the issue. `main` never holds an unarchived change. Default specification author: the implementer (usually the
agent); a maintainer approves.

## Archive executor

Whoever holds the branch (the implementer, or a maintainer who pulled a fork's branch), only after the maintainer's
command: every task ticked, then the archive skill, then `just spec-check`, then a commit. OpenSpec's sync skill also
rewrites main specs, so it waits for the same command. No workflow archives: no token can push to a fork, and a job that
could would be the only automation with write access to repository contents.

## Scope of changes

Three tiers, decided by the files a change touches; a mixed change follows the strongest tier.

| Tier     | Touches                                                                                                                                                           | Needs                                                                                                       |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Behavior | `plugin.json`, `mcp.json`, `mcp/`, `skills/`, `agents/`, `integrations/`, `scripts/generate/`, `scripts/validate/`, `tests/`, or a generated file's content       | A change with proposal, delta specs, design when warranted, tasks                                           |
| Harness  | `AGENTS.md`, `.agents/`, `.github/`, `scripts/` outside generate and validate, `justfile`, `deno.json`, `docs/`, `openspec/config.yaml`, root documents           | A change with `skip_specs: true` in `.openspec.yaml`: proposal, design when warranted, tasks, no delta spec |
| Exempt   | Spelling and formatting only, a Dependabot bump, regenerated files with no source change, wording in `README.md` or another human-reader page that states no rule | No change; the PR says which exemption applies                                                              |

The package gate applies to every tier that carries a change: a harness change's approval package is its proposal and
its design when warranted. Main specs change only through archived changes; a change that removes a capability corrects
the spec's Purpose in the same PR, named in its proposal and committed with the approval package.

## Initial bootstrap

The harness and the sample plugin were built in one conversation on 2026-10-26 under a plan the maintainer approved
there, before the PR labels workflow existed to record a label. The change `bootstrap-todo-tracker` records that
package; its draft PR carries the plan approval as its package approval, which confers no agent authority to archive,
merge, or release. The archive still waits for the maintainer's command.

## Update this file when

- OpenSpec is upgraded, replaced, or its layout moves, or the pinned CI version changes.
- The level, the approval owner, or a gate's mode changes.
- A second source of truth for any fact in the table above appears; merge it back.
- The archive executor changes, or the `spec-archived` check is renamed or removed.
- The tier table changes because a directory is added or moves.
