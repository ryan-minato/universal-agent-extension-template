# Contributing

> Coding agents: this page is an overview for human readers. Go to [AGENTS.md](AGENTS.md) and work from the knowledge
> base it routes you to. Where this page and the knowledge base differ, the knowledge base is right.

Thanks for wanting to help. This page explains how work gets done here so nothing about your first pull request
surprises you or us. The tools and checks in the repository hold everyone to the details; this page tells you what to
expect.

## What this repository is

A template for a coding-agent plugin that installs into Codex, Claude Code, Antigravity, and Pi from one Git repository.
The sample plugin, `todo-tracker`, exists to exercise every component type; adopters copy the repository and keep what
they need. Changes here therefore affect two audiences: people who install `todo-tracker`, and people who build their
own plugin from the template.

## How the work is organized

Every behavior the plugin exposes is a contract, written down before it is built. We use
[OpenSpec](https://openspec.dev): each capability has one specification under `openspec/specs/<capability>/spec.md`
saying what it does today. A change starts as an OpenSpec _change_ under `openspec/changes/`, holding a proposal, the
edits to the specifications, and a design when there is a real choice to explain. The maintainer approves that change
before any code is written; when the work is done the change is archived, which merges its edits into the
specifications.

Changes to the harness, scripts, CI, or documentation follow the same path without specification edits. A typo fix, a
Dependabot bump, or a regenerated file needs no change at all.

| Path                                                                                                                                           | What lives there                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `plugin.json`, `mcp.json`, `mcp/`, `skills/`, `agents/`                                                                                        | The plugin's shared core and runtime                          |
| `integrations/<framework>/`                                                                                                                    | What one framework needs beyond the core                      |
| `.claude-plugin/`, `.antigravity-plugin/`, `.codex-plugin/`, `.codex/`, `package.json`, `.mcp.json`, `mcp_config.json`, `hooks.json`, `rules/` | Generated by `just generate`; committed; never edited by hand |
| `scripts/`, `tests/`, `justfile`                                                                                                               | The Deno tooling and the checks                               |
| `openspec/`, `docs/`, `.github/`                                                                                                               | Specifications, the documentation site, and CI                |

## Working with a coding agent

Most changes here are written with a coding agent, and the repository is set up for it. The agent's rules live in
`AGENTS.md` and the files it points to; you do not need to read them to contribute, because the agent does.

| Agent                            | What it reads                                                                                                                                |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Codex, Antigravity, Pi, OpenCode | `AGENTS.md` and the skills in `.agents/skills/`                                                                                              |
| Claude Code                      | `AGENTS.md` directly (no `CLAUDE.md`: the plugin validator refuses one at a plugin root) and `.claude/skills/`, links into `.agents/skills/` |

You stay responsible for what you submit. Commits, pull requests, issues, and comments carry no AI or tool attribution,
and the person who commits answers for the change.

## From issue to release

1. **Issue.** Open one with the Bug, Feature, or Task form. Say what you need; the maintainer adds the area label at
   triage, and acceptance criteria come later, in the change.
2. **Branch and draft pull request.** Work on a branch for the issue and open a draft pull request whose first content
   is the OpenSpec change. Nothing is implemented yet.
3. **Approval of the specification.** The maintainer reads the change and discusses it with you on the draft.
   Implementation starts once the maintainer adds the label `spec:approved`; a workflow notes the approved commit in a
   comment and keeps the label only while the approved text is unchanged.
4. **Implementation.** Write the task list, the code, and the tests. Run `just generate` after touching a source and
   commit the generated files; a behavior change bumps `version` in `plugin.json` and adds a `CHANGELOG.md` section.
5. **Review.** Mark the pull request ready when `just check` passes and its description says how each acceptance item
   was verified. The required check `spec-archived` stays unreported on purpose until the change is archived, which
   blocks the merge without failing anything.
6. **Archive and merge.** When the maintainer asks for it, archive the change and push that commit; the maintainer
   squash-merges. The pull request title becomes the commit title, so it follows
   [Conventional Commits](https://www.conventionalcommits.org/), for example
   `feat(codex): add the install script for agent roles`.
7. **Release.** A merge that changed the version is tagged `v<version>` and published as a GitHub Release by the Release
   workflow, with the CHANGELOG section and the list of pull requests as its notes. A released version is never
   withdrawn; a mistake is followed by a higher version.

## Checking your work

Open the repository in its dev container: it has Deno, Node, just, OpenSpec, Zensical, and the Claude Code and Codex
CLIs. `just` lists the tasks; these are the ones you will use:

| Command                  | What it does                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `just check`             | Everything CI checks: formatting, lint, types, tests, generated files, plugin sources, specs, harness, docs |
| `just generate`          | Regenerates the native entry files from the sources                                                         |
| `just test`              | The unit, compatibility, and installation tests                                                             |
| `just smoke <framework>` | The installation smoke test for one framework, or the manual steps when its CLI is absent                   |
| `just docs-serve`        | Previews the documentation site                                                                             |

Generated files are never edited by hand; `just generate-check` fails CI when a committed one differs from its sources.

## Keep in mind

The repository is public. Credentials, tokens, internal hosts, and personal data never go into a file, a commit, an
issue, or a pull request. Everything in the repository is written in English.

To report a vulnerability, do not open an issue: follow [SECURITY.md](SECURITY.md).
